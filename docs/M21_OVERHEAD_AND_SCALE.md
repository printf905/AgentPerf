# M21 Instrumentation Overhead and Scale Characterization

## Goal

AgentPerf is itself a profiler, so M21 measured the cost of AgentPerf's own
instrumentation and offline workflows. The goal was engineering
characterization, not benchmark marketing:

```text
MEASURE -> CHARACTERIZE -> IDENTIFY BOTTLENECKS -> FIX MATERIAL PROBLEMS -> RE-MEASURE
```

The measurements below describe a tested local range, not a production support
limit or universal performance guarantee.

## Methodology

Benchmarks use deterministic local fixtures generated by
`scripts/generate_scale_fixture.py` and measured by
`scripts/m21_scale_benchmark.py`.

Committed evidence:

- `docs/data/m21_scale_results.json`
- `docs/data/m21_optimization_before_after.json`

Environment for the committed scale run:

| Field | Value |
|---|---|
| OS | macOS 14.4.1 arm64 |
| Python | 3.11.15 |
| AgentPerf | 0.4.0 worktree with M21 changes |
| Measurement | `time.perf_counter`, `time.process_time`, `tracemalloc` peak allocations |
| Warmups | 1 |
| Repetitions | 3 for scale cases |

`tracemalloc` reports Python allocation peaks inside the measured callable. It
is useful for relative local comparison, but it is not exact process RSS.

## Performance-Critical Path Audit

The inspected paths were:

- `TraceRecorder`, `trace_run`, `trace_llm`, `trace_tool`
- `ExperimentSession` finalization and artifact serialization
- artifact loading and trace parsing
- component token attribution and context-growth rows
- `CONTEXT_DUPLICATION`, `TOOL_OUTPUT_BLOAT`, `CACHEABILITY_HEADROOM`,
  `PREFILL_PATH_DOMINANCE`
- common-prefix and duplication metrics
- investigation grouping and materiality evidence
- `doctor`, `analyze`, `report`, `compare`, `check`, and suite checks

The two material problems found were:

- default traced LLM/tool IDs rebuilt and flattened the current run on every
  recorded call;
- `agentperf doctor` used full analysis even though completeness only needs
  trace loading and exact request correlation;
- prefix/cache analysis depended on pairwise prompt-prefix comparisons for
  larger correlated request sets.

## Runtime Instrumentation Overhead

Representative deterministic local loop: 20 tasks, 200 LLM calls, 40 tool
calls, 260 traced spans.

| Case | Median wall ms | P95 wall ms | CPU ms | Peak alloc MB | Approx per-span wall |
|---|---:|---:|---:|---:|---:|
| instrumentation off | 0.553 | 0.555 | 0.551 | 0.000 | 2.1 us |
| minimal tracing | 10.203 | 10.372 | 10.190 | 0.227 | 39.2 us |
| full components/usage | 12.099 | 12.540 | 12.027 | 0.337 | 46.5 us |
| full + artifact finalization | 106.183 | 110.116 | 101.607 | 2.464 | 408.4 us |

The relative increase over the no-op baseline is large because the baseline is
sub-millisecond. The more useful number is absolute overhead: tens of
microseconds per traced span before artifact finalization in this local loop.

`ExperimentSession` finalization includes analysis, finding generation, and
JSON artifact writes, so it is intentionally reported separately from span
entry/exit overhead.

## Artifact Growth and Offline Scaling

Scale fixtures use 2 tool calls per task, serving telemetry enabled, stable
request IDs enabled, full component attribution, and deterministic synthetic
prompt payloads.

| Tasks | LLM calls | Artifact size | Analyze median | Doctor median | Report median | Report size | Peak analyze alloc |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 10 | 61 KB | 12.9 ms | 2.6 ms | 21.9 ms | 46 KB | 0.36 MB |
| 10 | 100 | 591 KB | 128.1 ms | 11.9 ms | 191.7 ms | 246 KB | 3.44 MB |
| 100 | 1,000 | 5.95 MB | 1.45 s | 112.3 ms | 2.33 s | 2.27 MB | 34.28 MB |
| 500 | 5,000 | 30.10 MB | 8.47 s | 844.0 ms | not run | not run | 171.74 MB |

Artifact size is approximately linear in recorded calls and payload bytes for
this fixture shape. `doctor` is now much cheaper than full analysis because it
does not run detectors.

HTML report generation was characterized through 1,000 calls. Larger reports
are expected to scale primarily with embedded timeline/table output size and
were not generated in the committed run.

## Detector Scaling

Detector phase timing at 5,000 LLM calls:

| Phase | Median wall | Peak alloc |
|---|---:|---:|
| correlation | 1.6 ms | 0.96 MB |
| `ContextDuplicationDetector` | 1.21 s | 2.30 MB |
| `ToolOutputBloatDetector` | 175.8 ms | 1.02 MB |
| `PrefixCacheOpportunityDetector` | 6.90 s | 171.58 MB |
| `PrefillBottleneckDetector` | 10.1 ms | 1.29 MB |

`PrefixCacheOpportunityDetector` remains the dominant analysis cost on large
fixtures with serving telemetry and many correlated prompts. It now uses a
trie-based shared-prefix search instead of falling back to all-pairs prefix
grouping, but it still stores tokenized prompt structure proportional to prompt
volume.

## Compare and Check Scaling

Baseline/candidate pairs use 5 LLM calls per task.

| Tasks | LLM calls per side | Compare median | Check median | Peak alloc |
|---:|---:|---:|---:|---:|
| 1 | 5 | 20.3 ms | 20.3 ms | 0.27 MB |

## Optimizations Implemented

### TraceRecorder default ID generation

Problem: `record_llm_call` and `record_tool_call` used `len(self.to_agent_run()
...)` to assign default IDs. That rebuilt run structures on each call.

Change: keep recorder-local LLM/tool counters and lookup maps.

Measured result on the 260-span loop:

| Case | Before | After |
|---|---:|---:|
| minimal tracing | 18.7 ms | 5.9 ms |
| full tracing | 20.6 ms | 7.6 ms |

### Doctor completeness path

Problem: `doctor` called full `analyze_run`, including detectors, even though
readiness only needs the normalized trace and exact request correlation.

Change: build a minimal analysis report with `TraceCorrelator` only.

Measured result at 1,000 LLM calls:

| Case | Before | After |
|---|---:|---:|
| `doctor` | 3.72 s | 0.19 s |

### Prefix/common-prefix analysis

Problem: prefix/cache analysis and duplication metrics relied on pairwise
prompt comparisons in important paths.

Changes:

- `compute_duplication_metrics` finds largest common prefix from adjacent
  sorted token sequences and groups affected calls by first token;
- `PrefixCacheOpportunityDetector` uses a trie to find qualifying shared-prefix
  groups without all-pairs fallback.

Measured result at 1,000 LLM calls:

| Case | Before | After |
|---|---:|---:|
| `PrefixCacheOpportunityDetector` | 2.54 s | 0.75 s |
| full `analyze` | 3.59 s | 1.28 s |
| HTML report | 4.51 s | 1.94 s |

Focused detector/report tests confirmed existing finding semantics remained
stable after the change.

## Regression Guards

M21 added tests for:

- deterministic scale fixture generation;
- task/run/LLM/tool/serving counts;
- large fixture component-token totals;
- readiness and exact correlation counts on larger fixtures;
- compare matching across larger task counts;
- benchmark output schema, including zero-call cases;
- optimized duplication-prefix metrics preserving expected values.

The repository deliberately does not add tight wall-clock assertions to the
default unit test suite. Those are too machine-dependent. The benchmark harness
is reproducible and can be run manually or in a dedicated performance job.

## Tested Local Operating Range

Largest measured local fixture:

- 500 tasks;
- 5,000 LLM calls;
- 1,000 tool calls;
- about 18.6 MB of component text;
- 30.1 MB artifact directory;
- full `analyze` completed in 8.47 s median;
- `doctor` completed in 844 ms median.

This is a tested local engineering range, not a maximum supported scale.

## Limitations

- Measurements are from one local Apple Silicon machine.
- Timings are hardware and Python-version dependent.
- Fixtures are deterministic and synthetic; they exercise AgentPerf structure
  but are not production traffic.
- `tracemalloc` measures Python allocations, not exact process RSS.
- HTML report generation was measured through 1,000 calls, not 5,000.
- No distributed ingestion, production concurrency, GPU profiling, CUDA kernel
  tracing, or remote storage behavior was tested.
