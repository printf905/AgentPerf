# Real Telemetry Mapping: vLLM

Selected backend: vLLM OpenAI-compatible server.

This document is the contract for real telemetry ingestion. Missing backend
metrics must remain missing. Synthetic or schema-fixture values must never be
presented as real measurements.

Required vLLM server capabilities for the demo:

- OpenAI-compatible chat completions endpoint;
- client-provided `request_id`;
- prompt token details enabled so cached prompt tokens are returned;
- per-request metrics enabled so queue, TTFT, generation time, and inter-token
  latency are returned;
- token IDs returned where practical for exact tokenizer-aware analysis.

The adapter implemented in `agentperf/backends/vllm.py` consumes recorded
OpenAI-compatible response bundles generated by `scripts/run_vllm_real_demo.py`.

## Field Mapping

| AgentPerf field | Backend source | Raw field / event | Unit | Derivation | Reliability | Limitations |
| --- | --- | --- | --- | --- | --- | --- |
| `trace_id` | Client header / recording | `traceparent` trace ID recorded by demo runner | string | Client-generated and recorded | Direct when runner is used | vLLM response does not necessarily echo the trace ID. |
| `span_id` | Client or OTel export | recording field | string | None | Optional | Not required for MVP correlation. |
| `parent_span_id` | Client or OTel export | recording field | string | None | Optional | Not required for MVP correlation. |
| `agent_run_id` | AgentPerf runner | recording `agent_run_id` | string | None | Direct from client | Not a backend field. |
| `agent_step_id` | AgentPerf runner | record `agent_step_id` | string | None | Direct from client | Not a backend field. |
| `llm_call_id` | AgentPerf runner | record `llm_call_id` | string | None | Direct from client | Not a backend field. |
| `llm_request_id` | Client request to vLLM | request body `request_id`, recorded as `client_request_id` | string | None | Direct from client | Must be explicitly sent. |
| `serving_request_id` | vLLM response | response `id` | string | None | Direct from backend response | vLLM may normalize/prefix the submitted request ID. |
| `model` | vLLM response / request | response `model`, recording `model` | string | Adapter uses recording model | Direct enough for demo | Per-response model should be preferred if model routing is added later. |
| `provider` | AgentPerf adapter | constant `local` | string | None | Direct adapter metadata | Not backend telemetry. |
| `backend` | AgentPerf adapter | constant `vllm` | string | None | Direct adapter metadata | Not backend telemetry. |
| `started_at` / `ended_at` | Client runner | not implemented yet | timestamp | Unavailable | Unavailable | Client elapsed time is recorded in raw records, but normalized timestamps are not populated yet. |
| `prompt_components` | AgentPerf runner | record `prompt_components` | text | None | Direct from client | Backend sees serialized chat prompt, not AgentPerf's component boundaries. |
| `input_tokens` | vLLM response usage | `usage.prompt_tokens` | tokens | None | Direct | Exact according to vLLM tokenizer. |
| `output_tokens` | vLLM response usage | `usage.completion_tokens` | tokens | None | Direct | Exact according to vLLM tokenizer. |
| `prompt_token_ids` | vLLM response | `prompt_token_ids` | token IDs | Requires `return_token_ids=true` | Direct when enabled | Optional; unavailable if server/request does not return IDs. |
| `output_token_ids` | vLLM response | `choices[*].token_ids` | token IDs | Concatenated across choices | Direct when enabled | Assumes one generated choice for the demo. |
| `tokenization_mode` | Adapter | presence of token IDs | enum | `EXACT` when prompt token IDs are present, otherwise `APPROXIMATE` or `UNKNOWN` | Direct adapter label | Token counts may still be exact from usage even if token IDs are unavailable. |
| `queue_latency_ms` | vLLM per-request metrics | `metrics.queue_time_ms` | ms | None | Direct when enabled | Older/fallback second-valued keys are converted to ms. |
| `ttft_ms` | vLLM per-request metrics | `metrics.time_to_first_token_ms` | ms | None | Direct when enabled | vLLM defines this from scheduled time to first token, not necessarily client-observed arrival-to-first-token. |
| `tpot_ms` | vLLM per-request metrics | `metrics.mean_itl_ms` | ms/token | None | Direct when enabled | Mean inter-token latency is a TPOT proxy. |
| `prefill_latency_ms` | vLLM per-request metrics | `metrics.time_to_first_token_ms` | ms | AgentPerf uses TTFT as the closest request-level prefill proxy | Approximated | Pure prefill kernel time is unavailable from the OpenAI response. |
| `decode_latency_ms` | vLLM per-request metrics | `metrics.generation_time_ms` | ms | None when present | Direct when enabled | If missing, adapter derives `mean_itl_ms * max(output_tokens - 1, 0)`. |
| `prefix_cache_hit_tokens` | vLLM usage details | `usage.prompt_tokens_details.cached_tokens` | tokens | None | Direct when enabled | Requires prompt token details. |
| `prefix_cache_miss_tokens` | Derived by AgentPerf | `input_tokens - cached_tokens` | tokens | `max(input_tokens - cached_tokens, 0)` | Derived | Only meaningful when both input and cached tokens exist. |
| `kv_cache_used_tokens` | vLLM metrics | none per request | tokens | None | Unavailable | Server-level KV usage exists, request-level field remains `None`. |
| `kv_cache_capacity_tokens` | vLLM metrics | none per request | tokens | None | Unavailable | Do not infer from server configuration. |
| `kv_cache_evictions` | vLLM metrics | none per request | count | None | Unavailable | Server-level behavior may exist, but not request-specific in this adapter. |

## Directly Exposed

- response/request identifiers;
- exact usage token counts;
- prompt/output token IDs when requested and supported;
- queue time;
- time to first token;
- generation time;
- mean inter-token latency;
- cached prompt tokens.

## Derived

- prefix-cache miss tokens;
- normalized serving request linkage;
- decode latency when `generation_time_ms` is unavailable but `mean_itl_ms` and
  output tokens are present.

## Approximated

- `prefill_latency_ms`: set to `time_to_first_token_ms` because the OpenAI
  response does not isolate pure prefill kernel time. Reports and provenance
  label this approximation.

## Unavailable

- request-level pure prefill time;
- request-level KV cache occupancy/capacity;
- request-level KV eviction/reuse sequence;
- client-observed end-to-end TTFT unless separately measured by streaming client
  instrumentation.

## Fixture Policy

`examples/recorded_telemetry/vllm_openai_response_fixture.json` is a schema
fixture, not a real backend capture. It is labeled with:

- `fixture_kind`;
- `real_backend_capture: false`;
- a note that it is not benchmark evidence.

Only artifacts produced by a real vLLM server run should be placed under
`artifacts/real_vllm_demo/` and discussed as real telemetry.
